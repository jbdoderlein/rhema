# Transcript compaction

The session keeps its history whole. A request cannot. Cost grows with the session and the context window ends it, so `rhema-transcript` splits the two. The log is the caller's session, complete and untouched. The view is what one request carries, built per request under a byte budget. Nothing is deleted, and `zoom` gets any message back.

The budget is `max_view_bytes`, 256 KB by default. Below it the view is the log unchanged, so short sessions pay nothing. Past it the view becomes the block of sections covering the oldest messages, followed by the band from the cut to the end. The band is never cut, and neither is the current turn, the messages from the last user message on: the cut stops before them. The budget counts an image as one small message, not its encoded length: a provider tokenizes an image by its pixels, so charging the base64 would blow the budget over bytes compaction can never remove, since the digest drops image content and the band is never cut.

A flush fires only when the band cannot fit even with the cut at the oldest committed section, which means the total is over budget. The planner walks back from the current turn's start over whole messages that fit in the remaining allowance. A breach moves the cut forward far enough to leave at most half the allowance as the band, so the next flush waits for that much growth instead of firing on every step. The cut never moves back.

A flush chunks the newly sectioned range into sections of about `step_bytes`, 24 KB by default, capped at 128 messages. A section carries at least one message even when that message alone exceeds the step size. Boundaries fall between messages and never open on a tool result, so a call never ends up in one section with its result in another. A skill read gets its own section. A committed section keeps its range for good.

A section is a range, a text, and the origin of that text. The request sends the system prompt, the skills section, the block as one synthetic user message, then the band. Between flushes the block only grows by appending, so the prefix holds still and the provider's prompt cache can hit. A model fill that lands between flushes rewrites one section's text and breaks the prefix once; consolidation rewrites the block on purpose, which is why it is kept rare.

With no model wired, the text is mechanical. `summarize_range` walks the range once. Every user text is kept whole, flattened to a single line; past `USER_BYTES`, 8 KiB, the head stands and a marker states the message's full length, so a cut is visible and worth a `zoom`. The first two assistant texts are kept, each cut at 80 bytes with an ellipsis when longer. It counts tool calls by name, tool results, and results that failed. Only text blocks count: system text, call arguments, result bodies, and images are dropped. The output order is fixed, user texts then the tool line then the failure count then assistant heads, joined with `; `. Assistant text that is dropped leaves no marker; user text never leaves the block without one.

The tool line reads `N tool results (bash×3, edit×1)` when results are present, `N tool calls (...)` when the calls have no results in the range, and `N tool results` when results have no calls. Only the top three names are listed, with `, …` appended when more exist. Each section carries its address as `id+n|`, and the block header tells the model that `zoom(id, n)` returns those messages whole. Sections tile `[0, cut)`, so every original is reachable.

A `Summarizer` is an optional seam, not a dependency. At flush every section commits its extractive text at once, and the planner returns a `PendingSummary` holding the range's messages. A background worker calls `summarize`, and `commit_summary` swaps the answer in if the range still matches. A failed call leaves the stand-in, so no worker can block a request. Model text is capped at 8 KiB and up to four fills run at once. No production path sets a summarizer today, so the extractive text is what ships.

Skill bodies are pinned. The section covering a skill read carries the whole body verbatim, a re-read becomes a pointer to the section that already holds it, and a merge re-appends pinned bodies below the digest. The block itself is capped at `max_block_bytes`, 32 KB by default. Past it the two oldest sections merge and re-digest into one until the block fits, and every merge rewrites the prefix, so consolidation costs a cache break. A merge re-derives the union's digest from the log, and the user text survives it whole with it. That text does not compress, so a merge reclaims only the tool and assistant part of the ranges it joins: the block's floor is its user text plus its pinned bodies.

Four properties hold it together. Below budget the view is byte-identical to the log. Nothing is ever deleted. The band and the current turn go on the wire whole. The extractive path is deterministic and cannot fail, so a broken worker costs accuracy, never availability.
